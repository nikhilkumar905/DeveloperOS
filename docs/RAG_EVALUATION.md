# RAG Pipeline Evaluation

Evaluation of the DeveloperOS AI assistant (`chat-service/`), which answers questions about a developer's GitHub,
LeetCode, GeeksforGeeks, resume, activity and AI-generated insights using retrieval-augmented generation.

**Date:** 24 October 2026 · **Model:** Groq `openai/gpt-oss-20b` (temperature 0) · **Embeddings:** `all-MiniLM-L6-v2` · **Vector store:** ChromaDB

## Summary

The original pipeline answered **93.5%** of the test questions correctly and never invented facts, but it failed on
questions that span all of a user's repositories ("which repos use X?", "most starred repo"). In one case it
gave a confident wrong answer. Retrieval returned a handful of semantically similar documents, so for
portfolio-wide questions the evidence often never reached the model.

After the changes below, the pipeline answers **100%** of the 46 questions correctly (in two consecutive full runs),
with all required evidence reaching the model for every answerable question, no hallucinations, and a median
answer time of **0.62 s**.

| Metric | Before | After |
|---|---:|---:|
| **Answer accuracy** | 93.5% | **100.0%** |
| Fact recall (required facts present in the answer) | 94.3% | **100.0%** |
| Abstention accuracy (unanswerable questions) | 100.0% | 100.0% |
| Hallucination rate | 0.0%¹ | 0.0% |
| False refusals (answerable questions refused) | 2.4% | **0.0%** |
| Context hit rate (all needed evidence reached the LLM) | 92.7% | **100.0%** |
| Context recall | 93.9% | **100.0%** |
| MRR (rank of the first relevant document) | 0.50 | **0.94** |
| Context precision | 16.3% | 25.4% |
| Average context size (characters) | 2,077 | 1,933 |
| Retrieval latency p50 | 16.8 ms | 16.1 ms |
| Generation latency p50 / p95 | 801 ms² | **625 ms / 1,462 ms** |

¹ The baseline's one confident wrong answer ("most starred repository is docsy-search") is counted as an accuracy
failure rather than a hallucination, because the claimed fact did exist in its partial context.
² The baseline run's timings include rate-limit backoff, so its latency is indicative only. The final run was
paced to stay under the rate limit (no request was throttled).

## How the pipeline was evaluated

### Test profile

A fictional developer, "Jordan Lee" ([`chat-service/eval/fixtures/profile.json`](../chat-service/eval/fixtures/profile.json)),
so no real user data is involved:

- 12 GitHub repositories across TypeScript, Python, Go, Java, C++ and Shell. That is deliberately more than a top-k
  retriever returns, so portfolio-wide questions can't be answered by luck.
- LeetCode, GeeksforGeeks, resume (experience, education, certifications, hackathon), AI insights, and 10 days of activity.
- A knowledge graph generated by the backend's real `build_knowledge_graph` (101 nodes, 177 edges).

Every value has a single unambiguous correct answer, for example 412 LeetCode + 156 GFG = 568 problems in total.

### Questions and labels

46 questions ([`chat-service/eval/dataset.json`](../chat-service/eval/dataset.json)) in the 8 categories above. Each has:

- **Expected evidence:** the documents that must reach the model for the question to be answerable.
- **Required facts:** strings the answer must contain (with alternatives, e.g. "B.S." or "Bachelor"), matched
  case-insensitively on whole words.
- **Forbidden content:** e.g. listing the Vue project `recipe-box` as a React project.
- **Unanswerable traps:** Codeforces rating, Kaggle ranking, a job at Google, a Rust repository, a salary. The
  correct behaviour is to say the information isn't in the profile.

### Method

[`chat-service/eval/run_eval.py`](../chat-service/eval/run_eval.py) runs the production code path, not a copy:
`prepare_documents` → `ingest_documents` → `retrieve` → `select_context` → `answer`, against a throwaway Chroma
directory. It scores retrieval on exactly what the model sees (after the context-size budget) and scores answers
against the labels.

## Baseline findings

Retrieval was the weak point; generation was not. Every failure traced back to evidence that never reached the model:

| Question | Baseline answer | Why |
|---|---|---|
| Which of my repos have CI/CD set up with GitHub Actions? | "I don't have that information in your profile yet." | Neither CI repository was among the ~6 retrieved documents. |
| What is my most starred repository? | "Your most starred repository is docsy-search with 4 stars." (actually ledgerly, 31 stars) | Only 4 of 12 repositories were retrieved; the model picked the best of what it saw. **This answer looks right but is wrong.** |
| Which of my repositories are written in Python? | Missed `docsy-search` | Its repository document wasn't retrieved. |

Other observations:

- **Low precision and poor ranking.** The retriever used maximal-marginal-relevance search, which deliberately adds
  diverse (often unrelated) documents. For example, "What libraries does ledgerly use?" also pulled in `algo-notes`
  and the learning roadmap. The always-included profile overview was placed first, so the first relevant document
  sat at rank ~2 on average (MRR 0.50).
- **The context budget was not a constraint.** Only ~2,000 of the 6,000 allowed characters were used, so the misses
  were a retrieval-strategy problem, not a size problem.
- **Generation was reliable.** With the right evidence the model answered correctly, quoted numbers exactly, handled
  follow-ups, and refused every unanswerable question without inventing facts.

## Changes made

| Change | Where | Addresses |
|---|---|---|
| **Repository catalog document:** one line per repository with its language, libraries, stars, CI/CD, Docker and live demo, sorted by stars. Routed in for "which / list / how many / most … repos/projects" questions. | `indexer.py`, `rag_engine.py` | Portfolio-wide questions need every repository at once, which top-k over per-repo documents can't guarantee. |
| **Explicit fields in the catalog:** every row states every property, including "GitHub Actions CI/CD: no". | `indexer.py` | See the iteration note below. |
| **Hybrid retrieval:** BM25 keyword ranking fused with embedding ranking (reciprocal rank fusion), replacing MMR. | `rag_engine.py` | Exact names like `socket.io`, `pytest` or `FastAPI` are matched lexically, and noise is reduced. |
| **Evidence first, overview last** | `rag_engine.py` | The model sees targeted evidence first (MRR 0.50 → 0.94). |
| **Name variants:** "trailmix api" matches `trailmix-api` | `rag_engine.py` | Users rarely type hyphens. |
| **Context packing:** skip a document that doesn't fit instead of stopping | `rag_engine.py` | A large document can no longer push out smaller relevant ones. |
| **Prompt rule for list questions:** "check every item and list only matches; don't show your working" | `rag_engine.py` | See the iteration note below. |
| **Index versioning:** existing users' indexes are rebuilt automatically on their next message | `rag_engine.py` | Everyone gets the catalog without clicking "Update Knowledge Base". |

### Iteration note: why the evaluation mattered

The first version of the catalog fixed retrieval completely, but two answers got *worse*. The model listed
non-matching repositories:

- For CI/CD it confused "has Docker" with "has GitHub Actions", because the catalog only mentioned CI when present.
- For Python repositories it "thought out loud", listing every repository before concluding.

Stating every field explicitly for every row (including "no"), plus a prompt rule for list questions, fixed both.
The final answers are exactly `ledgerly, pulse-monitor` and `trailmix-api, docsy-search, weather-cli`. Without the
labelled set and the forbidden-content checks, this regression would have shipped unnoticed, since retrieval
metrics alone looked perfect.

## Limitations

- **One synthetic profile and 46 questions.** This is enough to find and fix systematic failures, but not a statistical
  guarantee for every user's data. Profiles with hundreds of repositories rely on the catalog's 40-repository cap
  (most starred first).
- **String-match scoring.** Required facts are checked by whole-word matching, not by an LLM judge. This is
  deterministic and cheap, but a correct paraphrase that omits the labelled term would be marked wrong. All failures
  in both runs were manually reviewed and were genuine.
- **One sample per question** at temperature 0. Both final runs scored 100%, but rare non-deterministic misses are
  possible.
- **Context precision stays modest (25%)** by design: keyword routes add every document of a matching type (e.g.
  both coding platforms for a "problems solved" question), trading precision for recall within a small context budget.
- **Free-tier limits.** Groq allows ~8k tokens/minute, so a full run takes ~15–18 minutes.

## Reproducing

```bash
cd chat-service
.venv/bin/python eval/run_eval.py --label baseline-rerun --retrieval-only   # seconds, no LLM calls
.venv/bin/python eval/run_eval.py --label my-run --pace 20                  # full run, ~18 min
.venv/bin/python eval/compare.py improved my-run
```

Raw per-question results (retrieved documents, answers, scores) are in
[`chat-service/eval/results/baseline.json`](../chat-service/eval/results/baseline.json) and
[`chat-service/eval/results/improved.json`](../chat-service/eval/results/improved.json). See
[`chat-service/eval/README.md`](../chat-service/eval/README.md) for the label format.

*Transparency note:* after the baseline run, the five aggregation questions were updated to also accept the new
catalog document as valid evidence (it contains every repository). This does not change any baseline number,
because the baseline had no catalog document.
